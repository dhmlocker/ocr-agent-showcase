模型调用需求

产品的工程框架已经就绪，下一阶段的核心工作是对大语言模型与视觉 OCR 模型做系统性实测。 本页说明产品需要哪些模型能力、以什么方式调用、用量如何约束——所有调用经由统一的授权与预算机制，用量可控、可审计。

为什么需要模型

三类核心场景，决定了产品的能力上限

产品在无模型配置下也能运行（规则模式），但识别质量与语义理解的提升都依赖模型实测与选型。

文档识别与解析验证

扫描件合同的高质量识别依赖多模态视觉模型（逐页图片识别 + 版面坐标）与文档解析服务（整本版面 / 表格还原）。 哪家引擎对中文合同扫描件的文字、表格、盖章干扰更稳？坐标能否支撑页内定位？这需要真实调用量来回答。

合同语义抽取与分析

深度合同分析需要模型把非结构化条款转成结构化结果：当事人、合同金额、逐笔付款安排、条款义务。 对模型的中文合同理解、结构化 JSON 输出稳定性、拒答幻觉（value 必须取自原文）都有明确要求。

Agent 智能问答

Agent 按轮次调用模型做工具选择与最终作答，要求模型稳定输出决策 JSON、忠实引用工具返回的原文、 证据不足时如实降低置信度。不同模型的多轮决策稳定性差异需要横向对比验证。

评测计划

下一阶段的模型实测计划

所有评测使用脚本生成的合成合同样本（真值已知、可复现、无敏感信息），绝不外发真实合同。

  • 识别质量基线 对不同视觉 OCR / 解析服务实测扫描件识别的字符错误率（CER 评测口径已在运行识别前固定）、表格还原完整率与坐标准确率。
  • 抽取质量对比 用同一组合成样本横评不同大模型的字段抽取准确率、结构化输出稳定性与引文忠实度（产品自带逐字证据校验，可直接量化）。
  • Agent 决策稳定性 对比各模型在多轮工具调用中的决策成功率、平均轮次与无效调用率。
  • 响应与成本 记录各模型的响应延迟、限流表现与 token 消耗，形成「能力 × 质量 × 成本」选型矩阵。
  • API 稳定性测试 验证 401（Key 无效）、429（限流）、超时与网络异常下的用户提示、重试与取消行为。
  • 量化报告 评测脚本与基线工具已随项目开发（CER 计算、语义抽取评测、离线统计），评测结果形成可复查的报告。
  • 选型落地 基于评测结果为「合同分析」「Agent 决策」「扫描件 OCR」分别给出推荐模型与降级方案。
  • 边界重申 产品当前未配置任何商业模型服务；云端评测仅使用合成样本与已获明确授权的演示文件，且逐次授权可随时拒绝。

模型效果，用数据说话

下一阶段的实测将建立识别质量与引文忠实度的量化基线，完成模型横向对比与选型，并验证 API 稳定性。 所有调用经由产品的授权与预算机制，用量可控、可审计、可取消。
